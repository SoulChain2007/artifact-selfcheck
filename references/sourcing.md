# 溯源复核：怎么搜、怎么核、记什么、别踩什么

本文件规则依据：核查要能**独立复现**，来源的可信度必须**当场读出来**而不是凭记忆（引文核查的基本要求）；
检索式用**本域术语**而不是自家模块名，否则检出来的东西与结论不同口（信息检索基本要求）；
单一来源撑多条互相独立的结论会掩盖证据不足，承重结论需要**多源交叉**；
主动搜索反面证据可抑制确认偏差（confirmation bias）；二手转述不构成来源。

## 第 0 步：按主题搜（这一步不能省，省了就等于没做溯源）

缓存不是答案。项目里往往有一份「已核实来源清单」——它是**缓存**，只能回答「这条来源我核过」，
回答不了「这条来源覆盖当前这个主题」。所以顺序固定是：

1. 把本轮每个承重结论写成**主题关键词**：用本域的术语（不是模块名、不是文件名），中英各一份便于检索。
   例：「交互矩阵 interaction matrix」「可读性预算 legibility budget」「先兆 telegraph」
   「禁区覆盖率 forbidden-region coverage」——而不是「InteractionCore 相关资料」。
   **主题词从任务画像来，不临场想词**：取 `selfcheck.md` 第 0 步任务画像的第 ④ 栏（从任务文本承重结论里
   抽出的领域术语），每条承重结论至少 1 个中英术语对；画像没覆盖到的才允许现场补，
   补的词要写「画像未覆盖，现场补：…」。
2. 拿关键词去搜：有 `web_search` / `WebFetch` 就用；没有就用 shell 调 GitHub API 读 star、
   curl 论文页 / DOI 页 / 权威索引读引用数。
3. 命中候选按阈值逐个筛，**落选的也要写落选原因**（不够引用数 / 不是同行评议 / 主题不对口）。
4. 再回头看缓存：缓存里的某条**确实覆盖这个主题**才能引用，并写明「命中哪一条 + 为什么覆盖」。
5. 留下**检索记录**：每个主题一行——关键词 / 检索面 / 命中候选数 / 入选与落选原因 / 访问日期。

判据：**整轮没有任何按主题的检索记录 ⇒ 判本轮溯源复核未做。**
⛔ 不许用「本批无新引用，故无现场核义务」当整段免检的理由。

## 第 0.5 步：检索面分层与检索式模板

**检索面按可用性降级使用；降级要在报告里写明降到了哪一层。**

| 层 | 手段 | 适用 |
| --- | --- | --- |
| 1 | `web_search` / `WebFetch` 工具 | 首选，能直接读页面 |
| 2 | 命令行取数：GitHub API（star / archived / pushed_at）、DOI 页、出版商页、标准组织页 | 工具不可用时 |
| 3 | 权威索引：Semantic Scholar / OpenAlex / 会议官网（读引用数与年份） | 论文类来源 |
| 4 | 无网络 | **判本轮溯源复核降级**，写「本轮无法联网，哪些结论因此只有弱依据」，⛔ 不许凭记忆补读数 |

**检索式模板**（`<...>` 里换成第 0 步的术语）：

```
<域术语> <断言或方法>              # 基础式，英文用英文术语再跑一遍
<域术语> (survey|benchmark|guidelines|standard) (2020..2026)
<域术语> "in practice" OR "field report" OR "postmortem"   # 找落地经验与失败案例
site:github.com <域术语> <技术关键词>                      # 找专业仓库
"<域术语>" (failure|pitfall|anti-pattern|limitation)        # 反面证据，必跑一条
```

**每个承重主题至少两条检索式**（一条正面、一条反面），并记录命中数。
⛔ 关键词里出现自家模块名 / 文件名 ⇒ 该次检索不算数（检出来的东西与结论不同口）。

## 第一步：找到本项目的阈值

阈值是**项目参数**，不是这个 skill 的常数。按顺序找：

1. 项目调度目录 / 口径文件（例如项目自带的「用户指令与口径」类文档、交接总纲）里用户当场给的标准
2. 项目自己的溯源基线文档（如果已经维护了一份「已核实来源表」，直接复用，但**新结论仍要现场核**）
3. 都没有 ⇒ 按下面的**来源层级**判断，并在报告里明写「本项目未给数值阈值，按层级判断」

层级（从强到弱，未给阈值时的默认）：
官方标准/规范/规范草案 > 同行评议论文（附引用数）> 官方文档/官方仓库 > 高星专业仓库 > 技术博客/问答

给了数值阈值时，把阈值当**准入线**而不是「参考值」：不达标就明写「弱依据 + 理由」，
⛔ 不许把 200 引用写成「约 600」这种擦边话术。

## 第二步：每个关键结论配一条来源记录

一条记录至少要有：

| 字段 | 要求 |
| --- | --- |
| 结论 | 它撑的是哪一句具体的话（要能追到报告里的编号） |
| 来源 | 标题 + 年份 + 作者/机构（论文）/ 仓库全名（GitHub） |
| 读数 | 引用数 / star 数**当场读到的数字**（不是记忆里的） |
| **支撑句摘录** | 从来源里摘 **≤ 2 行原文**（或仓库里哪个文件/哪个小节），回答「哪一部分支持我这句话」 |
| 位置 | URL 或 DOI |
| 访问日期 | 你实际看它的日期 |
| 判定 | 达标 / 弱依据（写原因） / 核不到（写为什么） |

**支撑句摘录是本轮新增字段**，专治最常见的假达标：引用了一个真论文，但那篇论文说的不是这件事。
摘不出原文 ⇒ 判「不支撑」，降为弱依据或换来源。

## 第三步：怎么核（现场，不许凭记忆）

- GitHub：仓库页面或 GitHub API 读 star 数；顺手看最近提交时间与是否归档（一个常年不动的仓库不算活参考）
- 论文：优先在原始出版方/DOI 页或权威索引（如 Semantic Scholar / OpenAlex / 会议官网）读引用数；
  引用数会随时间变，记下读到它的日期
- 标准/规范：核对**版本号与发布方**，并把「哪一版」写进记录（写「按 ISO 规范」而不写版本 = 没记录）
- ⛔ 二手转述不算来源：博客说某论文有 5000 引用 ≠ 你核过
- 被项目点名禁用的来源，直接不用，并说明它被禁用的理由（是项目政策给的还是你判断的，要分清）
- **承重结论多源交叉**：≥2 个互相独立的来源；只有单一来源时，必须再跑一条反面检索并说明为何仍采信

## 第四步：时效复核与跨轮多样性（防「每轮都是同几份」）

**时效复核**：复用一个核过的来源时，本轮只允许「复核它的版本 / 更新时间 / 是否被取代」，
⛔ 不许直接复用上一轮的读数（读数会变，尤其是 star、引用数、标准版本）。

**多样性约束（硬性，专防「每轮都捞同几份文件」）**：

- 同一主题 / 同一产物连续复核时，本轮来源集合与上一轮的**重合度 ≤ 50%**；
  例外：版本固定的标准与规范、以及被项目点名的基线文档（例外要在报告里写明）。
- 每轮**至少 1 条上一轮未出现过的新来源**；做不到就写「本轮为纯复核、无新结论」，
  并列出本轮实际核到的更新时间作为凭据。
- 同一份来源在同一份产物里支撑 ≥3 条**互相独立**的承重结论时，
  必须说明它凭什么同时覆盖这三件事；说不出就按证据不足处理，另找来源。
- 检索面也要换：不要每轮只用一个检索面或一个站点。

## 反模式清单（发现即判该条复核无效）

- 整轮只复述项目自带的「已核实来源清单」，没有任何按主题的检索记录（= 溯源复核未做）
- 每轮都捞同几份来源、没有新来源也没有复核凭据（= 多样性失效）
- 用「本批无新引用」给自己的整段免检找理由
- 凭记忆写引用数 / star 数，或写「约」「数百」「上万」而不给当场读数
- 关键词用的是模块名 / 文件名，而不是本域术语
- 引用一篇二手综述而不核它自己引了什么
- 引用了真来源，但摘不出支撑那句话的原文（只有标题对得上）
- 用同一个来源撑三条互相独立的结论而不解释覆盖理由
- 把「找不到达标来源」写成「所以按经验判断」，却不标明这是弱依据
- 只在报告里写「已核实」而不留 URL / 日期 / 读数
- 核了来源但没核它的时效性（被取代的旧标准当现行标准）
- 只搜了一面，从未尝试找反面证据

## 输出形态

## 外部方法准入闸门（Source Intake Gate · 2026-09-26 加）

**问题**：查网学来的东西如果"全都学"，skill 就被污染了。这不是假想 ——
`BadSkill`（arXiv **2604.09378**）证明第三方 skill 可以"看起来无害"，把恶意行为藏在随附的模型/文本里，
这是**供应链风险**；`AutoWorldBuilder`（arXiv **2607.09403**）把"**缺乏自动化质量保证**"列为世界构建的三大挑战之一。
所以：**外部学到的东西默认不可信，必须过闸**。

### 一、每条外来方法都要登记一行（`source_intake.jsonl`）

| 字段 | 要求 |
|---|---|
| `source` | 来源标题 + 年份 + 作者/机构（论文）或仓库全名（GitHub） |
| `surface` | 检索面（arXiv / GitHub API / DOI / 官方文档…） |
| `reading` | **当场读数**（引用数 / star / 版本号）；读不到写「N/A + 原因」，⛔ 不许凭记忆填 |
| `quote` | **支撑句摘录**（≤2 行原文）—— 回答「哪一部分支持我这句话」；摘不出就不算核过 |
| `counter` | **反面检索记录** —— 搜过「它的失败 / 局限 / 反例」吗？结果是什么（只搜支持自己的证据 = 确认偏差） |
| `target` | 学来后用在哪（文件:节） |
| `verdict` | `adopt` / `weak` / `reject`（**拒收也要留一行**，否则下次会再学一遍） |
| `detector` | 准入后**由哪个检查器检出** —— ⛔ 不许把"没有任何检查器能检出"的判据收进来 |

### 二、准入闸门（机器判据）

```
python scripts/source_intake.py --ledger <source_intake.jsonl>
```

**FAIL 条件**：缺 `quote` / 缺 `counter` / `verdict=adopt` 但 `detector` 为空 / 行不是合法 JSON。
⛔ 台账不过闸 ⇒ **不许把那批外部方法写进 skill**（这就是"防污染"的执行点，而不是一句提醒）。

### 三、三条硬规矩

1. ⛔ **不许整段搬运**外部方法文本：改写 + 注明出处 + 写明「本项目如何裁剪」；
2. ⛔ **不许把低层级来源升格为硬判据**（博客 / 无 star 仓库 / 单一未复核来源 ⇒ 最高只能到 `weak`，
   并且它只能**提示**检查方向，不能当"达标线"）；
3. ⛔ **一次只准入一处**（守规则预算），且准入后必须**能被现有检查器检出** —— 引入"检测不到"的判据
   等于给自己加了一条永久失效的规则。

### 四、自创方法要如实标注（本轮实测）

没有外部先例的方法（例如本项目的「世界内可达性链 / 概念理解链 / 结构审计五问」，由用户提问方式抽象而来）
一律记 `verdict: weak`，并在 `quote` 里写明「自创：无外部支撑句」。⛔ 自创方法**不得**因为"好用"
就被写成"有依据" —— 它需要的是**独立复核与现场读数**，不是补一句引用。

在报告里给四张表：

1. **论据表**：结论编号 → 来源 → 当场读数 → 支撑句摘录 → 判定
2. **检索记录表**：每个承重主题一行——关键词（中/英）/ 检索面 / 命中数 / 入选与落选原因 / 访问日期
3. **跨轮多样性读数**：本轮来源数 / 与上轮重合度 / 新来源数（不达标原因）
4. **弱依据汇总**：哪几条只有弱依据、为什么、打算怎么补（必须同时出现在缺口清单里，不许被平均数冲淡）
