# 迭代回路：按证据维护这个 skill

维护目标：短清单、明确范围、独立复核与返工闭环。方法变化必须通过有效反例和成功对照；不以条目增长或自评分上升证明改善。

> ⚠️ 本文件只管「改判据」这一半。**这轮查得好不好怎么量**归 [quality.md](quality.md)；
> **什么时候该改、改完拿什么验证、无效怎么回滚**归 [learning.md](learning.md)。三份一起用，缺一份这个回路就断。

**3.0 范围与状态**：通用规则只保留跨域不变量；项目事实、配置阈值与案例须标项目、适用条件、读数日期及验证范围。历史案例是线索，不是当前事实；跨项目累计不直接触发当前项目改规则。候选方法与生效规则分开，候选→验证→准入→观察/关闭或回滚的唯一状态约定见 `learning.md`，复制、升版本、发行都不等于候选准入。

## 一、每轮收尾必须做的四件事（缺一件 = 本轮自检未收尾）

1. **写台账**（JSON Lines，保留六个基础键：batch / date / lens / class / fixed / verify；可加 project / project_class / scope / quality / change_id 等，不改写历史行）
2. **反查或变异抽检**：抽一条已判「通过」的断言复跑；或按 `scaling.md` 做一次变异抽检。
   结果落进报告固定一节「灵敏度与方式变化」。不通过 ⇒ 按 L5/L6 失效登记台账
3. **判是否维护**：按第三节的触发条件调查并作出决定，⛔ 不是「我觉得够了就行」
4. **写质量读数**：按所选档位在报告或任务已有记录中给出 G1–G6 结果 + 自检半场 / 查网半场各维度分 + 评级，
   并在台账行上挂 `quality` 键（写法见 [quality.md](quality.md)）。**没有质量读数的一轮不算收尾**，
   因为第四节的「有效性验证」需要它当对照读数。3.0 新模式仅由显式 `schema_version: 2` 启用；旧输入按 legacy 契约重算并标注，跨契约不直接比趋势。full/partial 保留 G5 单会话 D 上限，quick 依档位免 G5。

## 三、什么时候必须调查并作出维护决策

任一条在当前项目适用范围内成立 ⇒ 本批必须调查一个根因并作出决定，写明「候选改动 / 执行修复 / 无需改动及证据」。**必须响应不等于必须改规则**，候选未完成准入不得参与本轮验收：

- 当前项目相同适用范围内任一 class 累计 ≥2（同一 class 第二次出现）；跨项目聚合只作风险提示，先核适用性
- 出现「报告写了通过、其实没查」（L5/L6 失效）
- 某域特有证据来源连续两轮被漏掉
- 分母跨过换挡阈值却没换挡（见 [scaling.md](scaling.md)）
- 灵敏度读数连续两轮下降（检查能力在退化，即使没发现新缺陷）
- 某一类缺陷是靠**人提醒**才发现的（现有判据没抓住它）

判「本轮无需升级」是允许的，但**必须逐条论证**：把本轮每个 class 列出来，一条一条写
「现有哪一条判据已经覆盖它 / 为什么这次还是漏了 / 下次为什么不会再漏」。
⛔ 一句话结论不算论证（某项目第 1 批就栽在这里：升级判定只写「本轮未新增规则，六透镜已覆盖」）。

## 四、升级动作：CAPA，而且先做预算

按 **非符合 → 根因 → 纠正措施 → 有效性验证 → 关闭** 五步走，缺「有效性验证」不算升级完成：

| 步 | 要写什么 |
| --- | --- |
| 非符合 | 台账里的 class + 发生在哪一批（要有盘上证据，不是印象） |
| 根因 | 为什么现有判据没防住：是判据缺失、还是判据在但没触发、还是执行者绕过了 |
| 纠正措施 | 六选一：①加域证据条目 → `domains.md`　②收紧既有判据 → `lenses.md`　③改检查方式 / 计量 → `scaling.md`　④改迭代与复核方式 → 本文件　⑤改质量维度 / 硬闸定义 → `quality.md`　⑥改反馈来源 / 触发条件 / 回滚 → `learning.md`。⛔ 只在六条透镜都问不到时才加透镜 |
| 有效性验证 | 写清下一批的相关暴露样本、旧失败回放与成功负对照及其命令/读数，填入 verify 或关联验证记录；零缺陷且零暴露不能证明有效 |
| 关闭 / 回滚 | 完成准入后连续两轮有相关暴露样本、旧失败能检出且成功负对照不退化才可关闭；连续两轮有效验证失败则按基线提交或可取得的补丁及 SHA256 回滚，保留原因和状态，不改历史记录 |

**规则预算（硬约束）**：

- 必答问题清单 ≤ **10 条**；`lenses.md` 的透镜 = **6 条**；自主元评审一次只提出 **1 个变更单元**（一个根因＋适用条件＋独立可验证的行为变化＋回滚点）
- 想加一条规则，必须在同一次改动里**合并或删除**一条等量的旧规则，并在报告里写清合并了哪两条。
  **约束对象 = 新增独立验收义务**，不能靠把条款塞入子例、脚本、探针节或命名为「收紧」规避。单纯实现修复、等价措辞与域限定澄清不重复计数；新增默认必做检查则计数。历史 2.1.0–2.2.0 曾将脚本/探针等排除预算的做法保留在 changelog 供追溯，3.0 不再以它自动豁免。
- **用户明确授权的版本维护批**可处理多个有证据的独立单元，每项分别列触发证据、范围、测试、准入状态与回滚位置；不是自主元评审，不受单元数量限制，但不能免除验证，也不能用维护批名义扩权。
- 同一单元可以修改必要的正文、测试和记录，但须列文件与行为影响；同一文件内两个独立根因仍是两个单元。候选的状态转换遵从 `learning.md`，未准入不得冒充已验证的主规则。
- 依据：清单过长的边际产出为负（Haynes / Pronovost），加结构容易变成仪式（Meyer & Rowan / Merton）

⛔ 不许凭想象加规则；⛔ 自主元评审不许一次处理多个独立单元；⛔ 不许把「新增了 N 条规则」当成改进证据。

## 五、不许自评了事：独立复核怎么落地

自评“通过”本身不是证据；已经实际取得的客观读数仍可支持其范围内的结论。按优先级取外部证据：

1. **换执行者做一次独立复核（首选）**：把 skill 与最小产物交给**另一条线、另一个会话或另一个模型**，
   ⛔ 只给现实请求 + 产物本身，**不给结论、不给疑似缺陷、不给修复方案**（否则测的是服从性，不是检出能力）。
   复核者要独立重跑关键读数，并单独写出「我核了什么 / 我不同意哪一条 / 我改了什么读数」。
   是否可用取决于当前实际工具与权限，不能凭历史经验假定免费窗口存在；不得让自己换口吻扮演复核者。
2. **反查一条已判「通过」的断言**（每轮必做）：命令真的跑过吗？输出真的支撑这句话吗？
3. **变异抽检**（见 [scaling.md](scaling.md)）：往要检查的件里放入一个已知缺陷，看本轮检查能不能检出来。
4. 与上轮读数对照，专门找「同一分母、结论却变了」的地方。

独立复核者若也判通过，报告要写「独立复核：<谁> 核了 <什么>，结论 <一致 / 分歧点>」；
没做就在「未做项」里写明为什么，并按 quality.md 的档位/单会话约定处理；不得为满足复核要求自行扩权。

## 六、台账的第六个键：verify（有效性验证）

```json
{"batch":"<批次>","date":"<yyyy-MM-dd>","lens":"<哪条透镜失效或被绕过>","class":"<封闭词表里的码>","fixed":"<对应的返工件编号或改动位置>","verify":"<下一批的**命令级**验证读数：谁产出(执行者角色) + 用哪条命令 + 期望读数；还没验就写 null>"}
```

下列第 2/11 批为历史案例，保留当时根因与处置；其数字不充当本轮读数，当时「未新增规则」的表述不替代 3.0 的义务预算判断：

> **⛔ 命令级 verify（第 2 批 CAPA-1 收紧；第 11 批 CAPA-3 再收紧）**：`verify` 只写**结果**（如「四件齐」/「已落地」）而无**产出者角色 ＋ 命令**者，视为**无效**。
> 依据：某项目 `module_not_closed` 累计 ≥2——第④件「验证读数」曾因"人人以为是别人的活"而无产线（代码线说越界、文档线在等），
> 根因正是 `verify` 只写结果、不指名谁用哪条命令产出。本次只收紧 `verify` 键措辞，**未新增规则条目**（守规则预算）。
>
> **⛔ 跨线依赖须有落点（第 11 批 CAPA-3 收紧）**：`verify` 涉及**两条以上并行线**的交接时，除产出者角色＋命令外，**必须写明「落点文件路径 ＋ 落盘判据」**（下游线凭什么确认上游已产出），否则视为**无效**。
> 依据：某项目 `process_ossification` 累计 ≥2——派活写了跨线协议「A 先提交名单 → B 登记 → A 落文件」，但**未给名单落点文件**，两条并行线各自等对方 ⇒ **双方互等，产出为 0**（典型「持有并等待 ＋ 循环等待」）。
> 只写「A 先落盘 → B 再消费」而**不写路径**，等于没有协议。本次仍是**收紧既有 verify 判据**（守规则预算：未加规则条目、未加透镜）。

落盘位置按项目规定；项目没规定时放在与该轮产物同级的 `selfcheck_ledger.jsonl`，并在报告里写明路径。
调度器只读台账，不写台账、不改 skill：

（a）把当前项目适用范围内累计 ≥2 的 class 与「`verify` 为 null 且已过一批」的条目提示给设计侧，要求本批调查并作出维护决定
（b）把台账路径、封闭词表、「反查或变异抽检」、方式变化留痕写进每一批派活词
（c）把换挡阈值与灵敏度要求（分母规模）写进派活词，分母过线就要求换检查方式

## 七、谁来做、什么时候做

做本轮自检的那个执行者在收尾时按档位做齐第一节的四件事，并安排适用的独立复核或诚实登记未做。
⛔ 不许把「这轮太忙」「用户没要求」当理由跳过适用动作；小产物按 quick 契约执行，不能拿重流程覆盖其豁免。维护决策按第三节触发条件，允许有证据的不改。

## 八、产出形态（固定四件）

1. 台账一行（六键，class 取自封闭词表）
2. 报告「灵敏度与方式变化」一节（检出读数 / 抽了哪条断言或哪个变异样本 / 命令 / 真实输出）
3. 报告「独立复核与升级判定」一节（谁核的、分歧点、升级或合并了哪一条、有效性验证读数）
4. 报告里一行 `本轮方式变化：<改了什么> / 触发原因：<阈值、灵敏度下降或哪次失败>`；没变也要写「无（原因：……）」
