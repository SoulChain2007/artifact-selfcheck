# 自学回路：让每轮任务的反馈真的改到这个 skill 自己

已有的事实基础：加结构最容易产出仪式（Meyer & Rowan 1977，28113 引；Merton 1940，1366 引）；
清单的有效性来自**执行依从性与判据质量**而非条目数量（Haynes 2009 NEJM，5715 引）；检验手段的检出能力必须被测过
（DeMillo 1978 变异测试，2082 引）；LLM 评委有自评偏好，**自评不算证据**（MT-Bench，771 引）。
本文件把「每轮任务的反馈」接成一条闭环：**读数 → 统计 → 判断 → 一次一处的改动 → 命令级验证 → 无效则回滚**。

## 一、反馈从哪来（四路，缺哪路都要写明）

| 路 | 来源 | 提取什么 |
| --- | --- | --- |
| F1 质量读数 | 本轮报告第 10 节 + `quality` 台账行 | 哪个维度低分、哪些硬闸没过 |
| F2 台账统计 | `selfcheck_ledger.jsonl` 全量 | 各透镜检出率、`class` 复发、`verify` 为 null 的老化条目 |
| F3 独立复核 | 复核者的报告与分歧点 | 「复核者不同意哪一条」「复核者改了什么读数」 |
| F4 用户口径 | 循环任务报告里用户当场给的话、纠正、告警（幻觉 / 污染 / 漏检） | 被点名的问题类型——**优先级最高**，一轮内必须响应 |

F4 一旦出现，不等元评审时点，**本轮就要处理**：把用户点名的问题写成台账 `class`，并在报告里给出对应判据的改动或「不改的理由」。

长任务模式下另有一路**应用层**反馈：本轮质量读数 → 「下一轮针对性」（不是改判据，是定这个任务的下一轮重点）——
映射表见 [longtask.md](longtask.md) 第三节。改方法的回路仍归本文件，两路不合并。

**反馈要同时含成功与失败（第 2 版收紧，依据 arXiv `2608.02636`）**：受控实验显示，只喂失败样本与
喂「成功＋失败」会把修订导向不同结果。所以每轮报告在台账行之外，**还要写一行「本轮保持绿的部分」**
（哪些判据跑了、哪些域抽了样、结果没变）——只记缺陷会让下一轮把注意力全放到已经修好的地方。

**每轮对着冻结快照跑（依据 arXiv `2609.04869`）**：本轮开始时先冻结产物与技能库的快照（见 `selfcheck.md` 第①步），
整轮读的都是这个快照；⛔ 不许改完再回头改本轮的读数。技能库相对「不用技能」的增量价值本身也**未被充分证明**，
所以每一轮都要留下「这轮检查真的产生了新信息吗」的读数（低密度连续两轮 ⇒ 判 `ritual_report`）。

## 二、什么时候做元评审

**到点**：每 5 轮（项目可调）一次。
**触发**（不必等到点）：

- 任一 `class` 累计 ≥ 2（同类失败第二次）
- 任一质量维度连续两轮 ≤ 2 分
- 六条硬闸任一失败
- 出现 `self_assessment_drift`（自评分与复核分差 > 1）
- 连续两轮灵敏度 = 0 或下降
- B / D 两路（上轮 class、覆盖补偿）连续两轮取不到料
- 用户点名纠正（F4）

> **进化是稀疏的（依据 arXiv `2608.02636`：388 个候选里只有 55 个产生字节级不同的验证最优）**：
> 「本轮不改」是**合法且常见**的结果。为了让每轮都有动静而硬改一处，本身就是一个失效模式（记 `rule_accretion`）。
> 允许「本轮不改」，但必须逐条论证（见 `iteration.md` 第三节末），并给出本轮的读数作为「不需要改」的证据。

## 三、元评审四步（缺第 4 步不算完成）

### 第 1 步 统计（用脚本，不靠印象）

```
powershell -File scripts/selfcheck_quality.ps1 -Mode ledger -Ledger <selfcheck_ledger.jsonl 路径>
```

脚本给出：每个透镜的 `执行轮次 / 有产出轮次 / 检出率 / 最近连续零产出次数`、`class` 计数与 ≥2 清单、
`verify` 为 null 的条目及其老化批次数、以及带上 `quality` 的行的分数趋势。

**零产出 ≠ 该透镜没用**：一条判据连续 **3 轮**零产出，才进入「僵尸判据」候选，
且必须区分两种原因：① 该类缺陷确实已消失（保留，但降为抽样）② 判据太软、抓不到（换更硬的证据来源）。
⛔ 不许因为「这轮没抓到东西」就删判据。

### 第 2 步 判断

| 统计现象 | 判断 | 动作方向 |
| --- | --- | --- |
| 某透镜连续 3 轮零产出 + 该域有已知缺陷类型 | 判据太软 | 换更硬的证据来源（读文件 → 跑命令）→ `domains.md` / `lenses.md` |
| 某 `class` 累计 ≥2 | 判据缺失或没触发 | 按 CAPA 收紧既有判据（优先），⛔ 优先不加新条款 |
| 某质量维度连续两轮 ≤ 2 | 方法层缺失 | 改 `selfcheck.md` / `sourcing.md` 的对应步骤 |
| `verify` 长期为 null | 没有人真的验证 | 收紧 `verify` 写法（产出者角色 + 命令 + 落点文件） |
| 覆盖度 / 分片始终不动 | 换挡阈值不合身 | 调阈值 → `scaling.md`，并记录旧值 → 新值 |

### 第 3 步 改动（一次只动一处，守规则预算）

- 一次元评审**只改一处**：`domains.md`（加/改域证据）｜`lenses.md`（收紧既有透镜）｜`scaling.md`（改方式与计量）｜
  `selfcheck.md`（改流程 / 判据生成器）｜`sourcing.md`（改检索方法）｜`quality.md`（改维度定义）｜`learning.md`（改回路）
- 想加一条规则，**同时合并或删掉一条等量旧规则**，并在 `changelog.md` 写清合并了哪两条。
- 改动必须指明**触发它的台账行**（批次 + class + 日期），不许「我觉得这样更好」。
- 改动幅度上限：一次不超过「1 条判据 + 1 处措辞」。超过就拆到下一次元评审。

### 第 4 步 验证（命令级、可复现、且必须可回滚）

在台账 / `changelog.md` 里写 `verify`：

```
<下一轮由谁（角色）> 用 <哪条命令> 读 <哪个文件>，期望 <什么读数>
```

**准入闸门（第 2 版新增，依据 arXiv `2608.28638` 的 solve-and-reproduce）**：一处改动只有同时满足下面三条才算**准入**，
否则只当候选（留在 `changelog.md` 里，不进正文）：

1. **字节级可分辨**：新旧两版在某个读数上确实不同（不是措辞换了、看着更全）；
2. **换执行者复现**：由**不是本轮执行者**的人/会话，在没有本轮回溯提示的情况下重跑该读数并得到同一结论；
3. **不劣于 incumbent**：在至少一个基准读数上不差于改前版本——自进化技能从零长出来的版本，
   实测可能**打不过人工策划的版本、在弱模型上甚至打不过不用技能**（arXiv `2608.28638`），所以默认立场是「原版保留」。

有效性判据（二选一，写明用哪个）：

- 该 `class` 在验证轮不再出现
- 该质量维度分回升 ≥ 1 分且硬闸全过

**连续两轮验证无效 ⇒ 回滚**：把该处改回上一版（旧文本保留在 `changelog.md` 的对应行里），
并记一次 `rule_accretion` 或 `process_ossification`，说明这次改动为什么没生效。

## 四、阈值自适应（可以调，但不许为过关而调）

可调项：换挡阈值（分母规模）、抽样量、检索面数、来源重合度上限、质量维度权重、元评审周期。

每次调整必须记录：

```
旧值 <x> → 新值 <y>；依据 <哪几轮的什么读数>；验证读数 <下一轮看什么>；复核者 <谁>
```

⛔ **不许为了让本轮通过而降低门槛**（把硬闸改成「讨论后通过」、把下限调低、把维度换成更容易拿分的定义）——
这类改动一律记 `gate_shift`，本轮质量结果作废，并回滚到调整前的阈值。
降低门槛的唯一合法理由：**历史读数证明现值不合身**（例如分母只有 20 件却设了 150 的换挡线），
且必须有独立复核者确认。

## 五、自学边界（这个 skill 不许越界）

- ✅ 允许改：本 skill 自己的 `SKILL.md` 与 `references/*`、追加 `changelog.md` 一行、写台账与报告
- ✅ 允许读：项目产物、台账、门禁脚本输出、上轮报告、外部权威来源
- ⛔ 不许改：项目产物本体、门禁脚本的判定标准、调度状态（`state.json` 批次号 / `STOP.txt` / `*.done` 标记）、
  别人的 skill、用户的口径文件（发现口径过期只能**报告**，不能自己改）
- ⛔ 不许扩权：不许因为「验收需要」就给自己开新权限、新外部写操作
- ⛔ 不许删产物：过期件只改名 / 归档 / 登记

## 六、版本与四份安装的同步

- 每次改动：`SKILL.md` frontmatter 的 `version` 按 **semver** 递增——PATCH = 措辞 / 标注 / 格式级修正；
  MINOR = 判据层改动（新增或收紧判据、改检查方法、新增脚本或探针节）；MAJOR = 结构层改动（增删文件、
  改回路形状、不兼容的判据语义变化）。历史版本号（2.1.x 时代的「+0.1 / +1.0」旧约定）不回改，
  并在 [changelog.md](changelog.md) 追加一行。
- 同一个人的机器上常常存在**多份安装**（不同 agent 框架各有自己的 skills 目录，甚至是同一框架的多个版本），
  **改一份必须同步其余几份**，否则不同线路会按不同判据自检（判据分裂）。
- 每轮自检的开头做一次**漂移检查**（一条命令，几秒）：比对各安装的 `SKILL.md` 与 `references/*` 的 SHA256；
  不一致 ⇒ 记 `duplicate_truth_source`，以 `version` 最高的那份为准同步，并在报告里写明同步了哪几份。
- 各份安装**只有 frontmatter 允许不同**（有的框架只读 `name` + `description`，有的还需要 UI 元数据字段），
  正文与 references **必须逐字节相同**。

## 七、库级维护清单（技能库会腐烂，依据 SkillOps arXiv `2605.13716`）

单条技能都对，整库仍可能坏：检索不到、互相冲突、依赖漂移。所以元评审顺带过一遍这张表（每轮自检只做第 1 行，
元评审做全部）：

| 项 | 检查动作 | 判据 |
| --- | --- | --- |
| 安装漂移 | 四份安装 `SKILL.md` 与 `references/*` 的 SHA256 比对 | 正文不一致 ⇒ `duplicate_truth_source` |
| 僵尸判据 | `scripts/selfcheck_quality.ps1 -Mode ledger` 的零产出连续轮次 | 连续 3 轮零产出 ⇒ 区分「缺陷消失」/「判据太软」 |
| 内部悬空引用 | 逐个引用文件 `Test-Path`；`SKILL.md` 里的每个 `references/x.md` 都要存在 | 悬空 ⇒ `broken_reference` |
| 版本与台账一致 | frontmatter `version` 与 `changelog.md` 最新行一致 | 不一致 ⇒ `stale_artifact` |
| 依赖漂移 | 外部依据（论文/仓库）是否被取代；标准是否升版 | 被取代 ⇒ 换来源，别删引用 |
| 准入积压 | `changelog.md` 里「候选未准入」的行数 | 长期积压 ⇒ 元评审优先清理候选，不许再堆新候选 |
