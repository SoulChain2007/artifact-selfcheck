# 自学回路：让每轮任务的反馈真的改到这个 skill 自己

历史设计依据（以下引用量与研究结论是旧版记录，本轮未重新核验，不作当前读数或新规则的准入证明）：加结构最容易产出仪式（Meyer & Rowan 1977，28113 引；Merton 1940，1366 引）；
清单的有效性来自**执行依从性与判据质量**而非条目数量（Haynes 2009 NEJM，5715 引）；检验手段的检出能力必须被测过
（DeMillo 1978 变异测试，2082 引）；LLM 评委有自评偏好，**自评不算证据**（MT-Bench，771 引）。
本文件把「每轮任务的反馈」接成一条闭环：**读数 → 统计 → 判断 → 一次一处的改动 → 命令级验证 → 无效则回滚**。

**3.0 范围约定**：通用规则、项目配置、历史案例与候选方法分别标明。历史案例只作线索；其中数字、路径、环境行为与研究主张未经本轮复核，不当作当前事实。把项目经验提炼为通用规则前，必须写出适用条件、反例与验证范围；只在一个项目出现的缺陷，不自动成为其他项目的必查义务。

## 一、反馈从哪来（四路，缺哪路都要写明）

| 路 | 来源 | 提取什么 |
| --- | --- | --- |
| F1 质量读数 | 本轮适用的证据摘要/报告 + `quality` 台账行 | 哪个维度低分、哪些硬闸没过 |
| F2 台账统计 | `selfcheck_ledger.jsonl` 全量 | 各透镜检出率、`class` 复发、`verify` 为 null 的老化条目 |
| F3 独立复核 | 复核者的报告与分歧点 | 「复核者不同意哪一条」「复核者改了什么读数」 |
| F4 用户口径 | 循环任务报告里用户当场给的话、纠正、告警（幻觉 / 污染 / 漏检） | 被点名的问题类型——**优先级最高**，一轮内必须响应 |

F4 一旦出现，不等元评审时点，**本轮就要响应**：把用户点名的问题映射到台账通用 `class`，项目特有细节放 `project_class`；在报告里给出调查、候选改动或「不改的理由」。用户的目标与任务授权优先，但响应不等于跳过候选准入或把本项目口径推广到其他项目。

长任务模式下另有一路**应用层**反馈：本轮质量读数 → 「下一轮针对性」（不是改判据，是定这个任务的下一轮重点）——
映射见 [longtask.md](longtask.md) 第四节。改方法的回路仍归本文件，两路不合并。

**反馈要同时含成功与失败（历史研究线索不作为本轮事实依据）**：保留成功样本，才能检查修订是否损坏原本正常的行为。每轮报告在台账行之外，**还要写一行「本轮保持绿的部分」**
（哪些判据跑了、哪些域抽了样、结果没变）——只记缺陷会让下一轮把注意力全放到已经修好的地方。

**每轮对着冻结快照跑（历史研究线索不作为本轮事实依据）**：本轮开始时先记录审计输入快照（见 `selfcheck.md` 第①步）。需要修补时，分别标记「审计输入」「候选改动」「修后验证」的版本或内容哈希、时间与范围，后两者不得覆盖前者的读数；⛔ 不许改完再回头改本轮原始读数。技能库相对「不用技能」的增量价值本身也**未被充分证明**，
所以每一轮都要留下「这轮检查真的产生了新信息吗」的读数（低密度连续两轮且无相关覆盖/有效对照 ⇒ 调查是否 ritual_report；稳定回归没有新缺陷本身不算失效）。

## 二、什么时候做元评审

**到点**：每 5 轮（项目可调）一次。
**触发**（不必等到点）：

- 当前项目、相同适用范围内任一 `class` 累计 ≥ 2（同类失败第二次）；跨项目统计只提供候选风险，先确认当前项目适用性
- 任一质量维度连续两轮 ≤ 2 分
- 本轮档位适用的 G1–G6 任一失败（合法豁免不算失败）
- 出现 `self_assessment_drift`（自评分与复核分差 > 1）
- 连续两轮灵敏度 = 0 或下降
- B / D 两路（上轮 class、覆盖补偿）连续两轮取不到料
- 用户点名纠正（F4）

> **允许不改**（历史研究线索不作为本轮事实依据）：
> 「本轮不改」是**合法且常见**的结果。为了让每轮都有动静而硬改一处，本身就是一个失效模式（记 `rule_accretion`）。
> 允许「本轮不改」，但必须逐条论证（见 `iteration.md` 第三节末），并给出本轮的读数作为「不需要改」的证据。

## 三、元评审四步（缺第 4 步不算完成）

### 第 1 步 统计（用脚本，不靠印象）

```
powershell -File scripts/selfcheck_quality.ps1 -Mode ledger -Ledger <selfcheck_ledger.jsonl 路径>
```

先限定项目与适用范围，再取统计。脚本给出：每个透镜的 `执行轮次 / 有产出轮次 / 检出率 / 最近连续零产出次数`、`class` 计数与 ≥2 清单、
`verify` 为 null 的条目及其老化批次数、以及带上 `quality` 的行的分数趋势。

若现有统计器不能筛选范围，先给它提供已核对的当前项目台账，并保留筛选条件；不能把混合项目统计当当前项目读数。

**零产出 ≠ 该透镜没用**：一条判据在有相关暴露样本的检查中连续 **3 轮**零产出，才进入「僵尸判据」候选；无暴露样本写「无有效观察」，不当作成功或失效，
且必须区分两种原因：① 该类缺陷确实已消失（保留，但降为抽样）② 判据太软、抓不到（换更硬的证据来源）。
⛔ 不许因为「这轮没抓到东西」就删判据。

### 第 2 步 判断

| 统计现象 | 判断 | 动作方向 |
| --- | --- | --- |
| 某透镜连续 3 轮零产出 + 该域有已知缺陷类型 | 判据太软 | 换更硬的证据来源（读文件 → 跑命令）→ `domains.md` / `lenses.md` |
| 某 `class` 累计 ≥2 | 判据缺失或没触发 | 按 CAPA 收紧既有判据（优先），⛔ 优先不加新条款 |
| 某质量维度连续两轮 ≤ 2 | 方法层缺失 | 改 `selfcheck.md` / `sourcing.md` 的对应步骤 |
| `verify` 长期为 null | 没有人真的验证 | 收紧 `verify` 写法（产出者角色 + 命令 + 落点文件） |
| 覆盖度 / 分片始终不动 | 换挡阈值不合身 | 调阈值 → `scaling.md`，并记录旧值 → 新值 |

### 第 3 步 提案（自主元评审一次一个变更单元）

- 一次**自主元评审只提出一个变更单元**。单元 = 一个已记录根因、一组明确适用条件、一个可独立验证的行为变化及其回滚点；不能用「同一文件」或「措辞收紧」把多个独立义务藏成一处。落点可为：`domains.md`（加/改域证据）｜`lenses.md`（收紧既有透镜）｜`scaling.md`（改方式与计量）｜
  `selfcheck.md`（改流程 / 判据生成器）｜`sourcing.md`（改检索方法）｜`quality.md`（改维度定义）｜`learning.md`（改回路）
- 想加一条规则，**同时合并或删掉一条等量旧规则**，并在 `changelog.md` 写清合并了哪两条。
- 改动必须指明**触发它的台账行**（批次 + class + 日期），不许「我觉得这样更好」。
- 自主改动幅度上限：一个判据行为及其必要措辞、测试和状态记录；多处文件为同一单元服务时须逐项列清，不能顺带改另一根因。
- **用户明确授权的版本维护批可以包含多个独立单元**：逐项登记触发证据、范围、前后对照、测试、回滚位置与准入状态。维护批不受自主元评审的单元数量限制，但不豁免任何单元的证据与准入要求；用户授权不等于所有候选已经验证。
- 规则预算按新增的独立验收义务判断，脚本、探针、子例与「收紧」若增加默认必做项，同样计入；同一义务的实现修复不重复计数。

### 第 4 步 验证（命令级、可复现、且必须可回滚）

在台账 / `changelog.md` 里写 `verify`：

```
<下一轮由谁（角色）> 用 <哪条命令> 读 <哪个文件>，期望 <什么读数>
```

**准入状态**：每个单元记录 `candidate`（候选）→ `validated`（验证完成）→ `admitted`（准入）→ `observing`（观察）→ `closed`（关闭），失败可转 `rejected` 或 `rolled_back`。状态、证据与适用范围在变更记录中可追溯；部署/复制不等于准入。

**准入闸门（历史研究线索不作为本轮事实依据）**：一个变更单元只有同时满足下面三条才算**准入**，
否则只当候选（在 `changelog.md` 或候选记录中保存拟议补丁，**不进入当前生效的强制规则**）。候选若为审阅而放进正文，必须独立标注「候选、未准入、不参与验收」，不得伪装已验证；既有未闭环候选须补证或撤出生效规则：

1. **字节级可分辨**：新旧两版在某个读数上确实不同（不是措辞换了、看着更全）；
2. **换执行者复现**：由**不是本轮执行者**的人/会话，在没有本轮回溯提示的情况下重跑该读数并得到同一结论；
3. **不劣于 incumbent**：在已登记的成功负对照上不差于改前版本，旧失败样本能检出，并说明当前项目的适用条件；不能凭一个指标上涨就略过其他已知回归。原版保留至候选完成准入。旧版关于自生成技能可能不及人工版本的研究主张（历史研究线索不作为本轮事实依据）属于历史依据，不代替本地对照。

**验证样本三件套必须齐全**：相关暴露样本（有机会触发该判据）、旧失败样本回放、原本健康的成功负对照。分别记录数量、范围、版本、命令与结果；无相关暴露、零样本或未执行都写「未验证」，不据此关闭。不存在历史失败样本时，登记可解释的植入样本及其局限。

满足三件套后，有效性指标可二选一（写明用哪个），但指标本身不替代上述证据：

- 相关暴露样本中该 `class` 未复发，且旧失败能检出、成功负对照未退化
- 该质量维度分回升 ≥ 1 分且适用硬闸全过，且旧失败能检出、成功负对照未退化；前后必须使用同一评分契约

**连续两轮有暴露样本的验证无效 ⇒ 回滚**：把该单元恢复到已登记基线；无暴露样本为「观察不足」，不宣称有效。回滚依据用 Git 提交及文件路径，或可取得的正/反向补丁及 SHA256（同时登记基线、候选文件哈希），不得声称 changelog 摘要保存了完整旧文。追加 `rolled_back` 状态，保留原记录，并按根因记 `rule_accretion` 或 `process_ossification`；不把回滚叙事改成成功。

**评分兼容纪律**：保留自检/查网双半场和 G1–G6。3.0 新模式只由显式 `schema_version: 2` 启用；未显式启用的旧输入按 legacy 契约重算并标注，不能与新契约分数直接比趋势。G5 单会话降级的 D 上限适用于 full/partial，quick 按档位契约免 G5；不得借改评分契约宣称改动有效。

## 四、阈值自适应（可以调，但不许为过关而调）

可调项：换挡阈值（分母规模）、抽样量、检索面数、来源重合度上限、质量维度权重、元评审周期。

每次调整必须记录：

```
旧值 <x> → 新值 <y>；依据 <哪几轮的什么读数>；验证读数 <下一轮看什么>；复核者 <谁>
```

⛔ **不许为了让本轮通过而降低门槛**（把硬闸改成「讨论后通过」、把下限调低、把维度换成更容易拿分的定义）——
这类改动一律记 `gate_shift`，本轮质量结果作废，并回滚到调整前的阈值。
降低门槛的唯一合法理由：**历史读数证明现值不合身**（例如分母只有 20 件却设了 150 的换挡线），
且必须有独立复核者确认。

## 五、自学边界（这个 skill 不许越界）

- ✅ 允许改：本 skill 自己的 `SKILL.md` 与 `references/*`、追加 `changelog.md` 一行、写台账与报告
- ✅ 允许读：项目产物、台账、门禁脚本输出、上轮报告、外部权威来源
- ⛔ 不许改：项目产物本体、门禁脚本的判定标准、调度状态（`state.json` 批次号 / `STOP.txt` / `*.done` 标记）、
  别人的 skill、用户的口径文件（发现口径过期只能**报告**，不能自己改）
- ⛔ 不许扩权：不许因为「验收需要」就给自己开新权限、新外部写操作
- ⛔ 不许删产物：过期件只改名 / 归档 / 登记

## 六、版本与实际安装的同步

- 每次改动：`SKILL.md` 正文版本（可安装插件另与 plugin.json 的 version 对齐；平台元数据允许生成兼容变体） 按 **semver** 递增——PATCH = 兼容的实现修复、措辞 / 标注 / 格式修正；
  MINOR = 向后兼容的可选能力、检查方法或脚本；MAJOR = 不兼容的验收/评分/数据契约或默认强制行为变化。新增文件本身不决定主版本。历史版本号（含 2.1.x 时代的「+0.1 / +1.0」旧约定）不回改，
  并在 [changelog.md](changelog.md) 追加一行。
- 历史记录提到 Codex、国内版/国际版 WorkBuddy 与 CLI 家目录等多份安装；它们不是所有环境的必备目录。本次实际已知源路径为 `<user-profile>/.codex/skills/artifact-selfcheck`，维护副本为 `<maintenance-workspace>/artifact-selfcheck`；其余安装路径须发现后再登记，不能据历史简称宣称当前存在或已同步。
- 维护安装清单：实际绝对路径、角色（源/候选副本/部署/公开发行）、版本/提交、准入状态、内容哈希、访问与写入权限、最近实际检查时间；不可访问或需权限的路径标「未检查/待授权」，不扩权、不越过环境权限。源安装更新与向外发布分别以用户授权范围为准。
- 按任务档位和实际安装清单检查漂移；同一事实冲突记 `duplicate_truth_source`。**不以最高 version 自动覆盖**：先比较提交来源、准入状态、差异与项目例外，同版本分叉也须核；冲突未解决时报告差异并保留两份。
- 各平台允许不同的 frontmatter 单独校验；公共正文与 `references/*` 分别做内容哈希，不拿完整 SKILL 哈希差异误报允许的元数据差异。发行脱敏与项目裁剪须有映射和批准范围。只有实际写入并复核的路径才记「已同步」，本次复制维护不代表部署完成。

## 七、库级维护清单（按当前实际范围检查）

单条技能都对，整库仍可能坏：检索不到、互相冲突、依赖漂移。所以元评审顺带过一遍这张表（每轮按档位与实际安装范围检查第 1 行，元评审做全部适用项）：

| 项 | 检查动作 | 判据 |
| --- | --- | --- |
| 安装漂移 | 按实际清单比较公共正文与 references 哈希，平台 frontmatter 单独核 | 未解释的正文差异 ⇒ `duplicate_truth_source`；未知路径不声称已检查 |
| 僵尸判据 | 同项目同适用范围的 ledger 零产出连续轮次，结合暴露样本记录 | 连续 3 轮有效观察零产出 ⇒ 区分「缺陷消失」/「判据太软」；无暴露不判有效 |
| 内部悬空引用 | 逐个引用文件 `Test-Path`；`SKILL.md` 里的每个 `references/x.md` 都要存在 | 悬空 ⇒ `broken_reference` |
| 版本与台账一致 | SKILL.md 正文版本、插件 manifest 与 changelog.md 最新维护记录一致 | 不一致 ⇒ `stale_artifact` |
| 依赖漂移 | 外部依据（论文/仓库）是否被取代；标准是否升版 | 被取代 ⇒ 换来源，别删引用 |
| 准入积压 | 变更记录中 candidate/validated 未完成准入的单元 | 优先补证、拒收或撤出生效规则；未准入不参与验收，也不随复制/发行自动转正 |
