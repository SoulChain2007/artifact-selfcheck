# 六条透镜：完整问句、判据、不合格证据

六条透镜与产物类型无关。逐条过，每条至少给出「问句 → 读数 → 结论」三样。

## L1 声称↔实存（claims vs artifacts）

问句：
- 产物里每出现一次「已建 / 已有 / 已通过 / 已登记 / 已完成」，盘上对应的东西在哪？（给绝对路径）
- 那个东西的**内容**真的兑现了那句话吗？（不是「文件在」，是「文件里是这句话说的事」）
- 它的修改时间与声称的轮次/批次对得上吗？（防止拿旧件顶新账）
- 有没有「只登记在文档里、工程里没有」的条目？
- **这句话说的是哪一层？** 当产物同时存在「**本体层**」与「**表现层**」两套表述时，须核每句设定**在它自称的那一层**是否成立（例：世界架构文档写「人物卡 B–S」，须核它在**世界层**是否成立，而不只是在**表现层**成立）。**分层混写**是本条盲区——「文件在、话也兑现了」，但兑现的是**另一层**。（世界设计类项目第 1 批 CAPA：本批抓出 2 处「把表现层实体写进本体层规则」）

不合格证据：「我记得建过了」「文档 §5.1 里登记了」「上一批的报告说通过」。
合格证据：路径 + 关键内容片段 + 一条能复现的读取命令 + 输出摘要。

## L2 应有↔实有（coverage）

问句：
- 这次的**分母**是什么？它出自哪份规格文件/哪张清单/哪个编号体系？
- 分母里每一项，逐项判：实有 / 缺 / 名字不同但可能同一件 / 多余（规格里没有但盘上有）
- 有没有「规格说要 N 条，盘上只有 M 条」而报告写「已覆盖」的情况？**待建模块（下一批要建的模块）的门禁清单，是否在该模块第①件落地之前已落 checker —— 无 checker 的门禁一律记 `coverage_gap`，不得计入「已覆盖」**？（第 3 批 CAPA-2 合并收紧：合并进本条既有问句，未新增条目）

判据：分母必须是外部规格。**用产物清单当分母，是自我循环，直接判该条检查无效。**
输出格式固定三栏：`应有 | 实有 | 悬空`，并给两侧计数。

## L3 内部一致（consistency）

问句：
- 同一个数字/单位/公式在不同文件里是否一致？（阈值、倍率、上限、时间、坐标、帧率、采样率）
- 术语表里的名字与正文里的名字是否一致？（含大小写、全半角、中英混用、单复数）
- 编号体系有没有断号、跳号、重号、复用？（模块号、条目号、不变量号、图号、章节号）
- 日期与版本：文件头写的版本/日期，与它实际内容对应的版本对得上吗？
- 同一个概念在两个地方被定义了两次且定义不同——这类「双真相源」是本条最严重的发现。

不合格证据：「整体看起来一致」。合格证据：两处引用并排 + 差异点 + 谁该改。

## L4 引用完整（referential integrity）

问句：
- 每个指向别处的引用（文件路径、章节号、条目号、URL、图片名、资源 ID），目标存在吗？→ 悬空引用
- 每个产物都被至少一处引用吗？→ 孤儿件（可能该登记没登记）
- 有没有两个文件在讲同一件事（重名件 / 平行真相源）？
- 有没有内容已被取代、但文件名和正文看着还像现行的件？→ 过期件
- 改名/移动/归档之后，别处的旧引用跟着改了吗？
- **自动化检查器 / 门禁段的输出，在被写入工程结论前，必须抽检验证其解析逻辑与扫描范围**（例：`docs/<N>` 这类带编号的路径须按编号前缀解析、且须扫全树而非仅入口文件）；未抽检验证前，该读数判 `unverified_claim`，⛔ 不得作为「已通过 / 无问题」证据。（第 5 批 CAPA：实测某检查器只扫了 1 份文件，`docs/<N>` 解析全误报 186 条，而人工抽检那几个编号的文档其实都存在——此条透镜收紧即防「盲目采信检查器输出」这类失败）

过期件的默认处置：改名或归档 + 登记台账；⛔ 不静默删除。
- **命名型字段也要查引用闭合（2026-09-26 加）**：本条的"引用"不止 ID / 路径 / 编号，
  还包括**字段里直接写出来的实体名字**（材料、载体、出处、施术者…）。判据：值拆词后每个词都能命中同名条目；
  命中不了就是悬空，并按其被使用次数排优先级。⛔ 只查 ID 外键会漏掉整类洞。
- **同值占比过高即模板话（2026-09-26 加）**：同一字段在同类产物里被同一句话占满
  （经验阈值 ≥30% 且 ≥20 条）⇒ 判该字段为模板默认值，不算内容（属 L1 声称↔实存的弱化形态）。

## L5 可验证性（verifiability）

问句：
- 每条「通过」的断言，对应哪条命令？今天再跑一次还过吗？（**复跑，不要只复述**）
- 那条命令的退出码/输出里，判定标准是什么？（多少算过、失败长什么样）
- 这条验证覆盖的是「整个声称」还是只覆盖了一个更弱的东西？（例如跑了编译就宣称逻辑正确 —— 不合格）
- 验证脚本本身有没有可能只会说 PASS？（只断言常量、恒真条件、被 try/catch 吞掉的失败）
- 如果这条断言没法验证，为什么？能不能降级成一个可验证的弱版本并说清降级在哪？

## L6 注意力限制（attention limits）

问句：
- 分母有多大（文件数、条目数、字数、图数、任务数）？我这轮实际看了/跑了多少？
- 我是**抽样**看的还是**穷尽**看的？抽样的话抽样规则是什么、覆盖率多少？
- 剩下没看的那部分，最可能藏着哪类问题？
- 有没有「换了一批文件看，结论差不多，所以剩下不用看了」这种自我说服？→ 明确禁止
- 有没有被截断的输出（长列表、被省略的行、只看头尾）？截断处必须写明。

硬性要求：报告里必须有一节「未做项与原因」。没写 = 本轮自检不完整。

## 六条透镜的常见组合失效

- L1+L5 都做过，但 L2 的分母取自产物 ⇒ 全篇「通过」，实际缺一整块
- L3 只比了同类文件内部 ⇒ 跨层（文档 vs 数据 vs 代码）的数值冲突漏掉
- L4 只查了正文引用，没查文件名/编号 ⇒ 改名造成的悬空引用漏掉
- 全部透镜都跑了，但没有 L6 ⇒ 报告读起来像穷尽检查，实际只看了 10%
